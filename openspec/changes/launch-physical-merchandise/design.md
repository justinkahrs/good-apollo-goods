## Goals / Non-Goals

**Goals:** one understandable operator experience; live catalog updates; authoritative stock; recoverable payment processing; independently scoped Good Apollo services; and a complete order-to-shipment workflow.

**Non-Goals:** importing Vesper's framework, download models, production secrets, or customers; coupling releases of the two apps; creating a general warehouse platform. See the proposal for commercial scope exclusions.

## Decisions

### 1. Keep Astro; run a capped Node service on the existing VPS

Build with Astro's standalone Node adapter and run one Good Apollo web container behind the existing Traefik ingress. Keep static rendering for informational pages/assets, and render catalog-dependent pages/components, product details, admin, order status, and API routes on demand. Remove `getStaticPaths()` from dynamic product routes and resolve the slug at request time. Preserve existing URLs, brand, and design tokens. Set explicit CPU/memory limits and bounded request/image/job work; monitor host memory, swap, CPU, and disk so this service cannot consume the shared stack's capacity. [Astro rendering guide](https://docs.astro.build/en/guides/on-demand-rendering/), [Astro Node adapter](https://docs.astro.build/en/guides/integrations-guide/node/).

For launch, do not cache mutable catalog HTML or availability. A fresh request reflects a committed change within five seconds. Keep static assets and immutable image derivatives cacheable for customer speed. Stock is always rechecked at checkout even if the user holds an old page. Database failure produces an unavailable state and prevents checkout; it does not serve fake stock from seed data.

Use PostgreSQL with Prisma, borrowing Vesper's migration/domain-test patterns. Reuse the existing shared PostgreSQL server through the already isolated Good Apollo database, runtime role, and migration role. Keep TLS verification, transactions/row locking, bounded connections, backups, and isolated preview data. The VPS and PostgreSQL may share the host but Good Apollo must not share tables, schemas, credentials, auth sessions, or customer data with other applications. Pin compatible dependencies after checking the installed Astro 7/Node 22 toolchain.

Use Garage for a dedicated Good Apollo bucket and scoped access key per environment. Keep Garage private on the VPS data network. Route each authenticated, short-lived upload intent through the same-origin application endpoint; validate admin session, origin, content type, exact byte count and intent ownership before writing to Garage. Serve only sanitized derivatives through the application media route. Do not expose Garage's admin API, bucket listing, or unrestricted object reads. Garage has its own key-to-bucket permission model and does not support S3 bucket policies or object versioning, so use separate encrypted off-VPS backups and verify actual backup/restore behavior. [Garage S3 compatibility](https://github.com/deuxfleurs-org/garage/blob/main-v2/doc/book/reference-manual/s3-compatibility.md).

Use the existing Good Apollo sender identity and guarded Mautic delivery path for website transactional messages. The app's durable email outbox remains authoritative for dedupe, leases, retries, and uncertain outcomes. Add a private authenticated adapter for approved transactional messages; do not use Senna's global mailer identity or newsletter admission routes, and do not enable newsletter controls as a side effect. Mautic uses its configured outbound transport; it is not an SMTP server for the app. [Mautic email transport](https://docs.mautic.org/en/7.2/configuration/settings.html).

Alternative: migrate to Next.js and fork Vesper. Rejected because it would rewrite a working storefront and import digital-product complexity. Alternative: retain static content plus a Git-based CMS. Rejected because frequent stock/catalog updates would depend on deployments and still need a transactional payment backend. Alternative: use a hosted app/storage/email plan. Rejected for the current deployment because an existing VPS, isolated database, and guarded sender are available; revisit if measured capacity, uptime, or operator burden fails acceptance.

### 2. Use a focused Good Apollo admin and adapt Vesper patterns

Recommend three main navigation items, **Products**, **Inventory**, and **Orders**, plus a small settings/help area. Admin uses Astro-rendered forms with progressive enhancement; add a framework island only where image ordering or variant editing actually needs it.

| Approach                                   | Operator experience                                                                                   | Engineering/operating trade-off                                                                                                                                                 | Decision                                                        |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| Good Apollo admin + Stripe                 | One branded screen, dollar inputs, a size/color table, upload/reorder photos, stock, packing/tracking | Requires building and maintaining physical stock/order logic; reuses familiar Vesper patterns                                                                                   | Selected by owner                                               |
| Hosted commerce dashboard                  | Standard catalog, inventory, and fulfillment controls                                                 | Introduces a different commerce provider/dashboard, migration, recurring costs, and synchronization with this storefront; its payment model needs a separate integration choice | Valid fallback if operator acceptance of the custom admin fails |
| CMS/spreadsheet + standalone payment links | Familiar content entry                                                                                | No single transactional stock authority; catalog/payment/fulfillment can drift                                                                                                  | Reject for launch                                               |

The owner confirmed a simple Good Apollo admin using Vesper's patterns, along with U.S.-only shipping, guest checkout, and ready-to-ship stock. The comparison is based on this codebase and those needs, not a researched vendor pricing comparison. Switching to hosted commerce changes this design and must revise the change before implementation.

Owner-requested September 30 refinement: make the studio product editor as considered as the storefront and default to one fixed piece. Use open brand typography and a two-column workspace with a compact price/availability/visibility sidebar; stack on phones. Fixed dimensions and exterior/lining belong to description/details. Hide size/color generation, SKU/stock-alert controls and secondary content/settings behind optional sections while retaining their existing capabilities. Existing single-item edits preserve the default variant's identity and stock. Automatically select that identity on the public item page without an artificial size choice. The inventory improvement change lets operators select photos and initial counts before saving; product-owned transfers begin after draft creation in the same editor. Stock changes reuse the audited adjustment workflow inline and on Inventory.

Operator workflows:

1. **New product:** name, description/details, category, optional audience/material/care fields, price as `$72.00`, and photos. A product with no options gets one hidden default variant.
2. **Variants:** choose up to two option names, such as Size and Color, and enter values. Generate combinations, remove unwanted ones, override price where needed, and enter initial stock in a small table. Auto-generate SKUs; allow optional edits. Avoid asking the operator for database or Stripe identifiers.
3. **Photos:** select several images, see progress/thumbnails, reorder, select cover, optionally customize generated alt text, optionally associate with a variant. Save draft at any stage. Errors retain form data.
4. **Publish:** show an ordinary-language checklist of missing name/description/category, valid active variant/price, and ready real cover/alt text. Zero-stock products can publish as sold out. Existing imported placeholders cannot satisfy the checklist.
5. **Inventory:** show Available to sell, Held at checkout, and Unsold stock. Add stock, remove damaged stock, record off-site sale/consignment transfer, or set an actual count of unsold stock; show a reason and resulting balance before saving. Explain that paid orders awaiting packing are already sold and excluded from this count.
6. **Orders:** default to Paid / To pack. Open order, print a packing slip, buy a label externally, then enter carrier/tracking and mark shipped. Financial and fulfillment badges remain separate. Attention items and failed email deliveries are visible without exposing implementation jargon.

Every editing form carries a revision; a stale edit reports a conflict and offers refreshed values instead of overwriting another session's work. Published edits are atomic and must pass publication validation; draft work does not leak publicly. Archive hides purchase/listing while retaining order history; existing reserved checkout terms remain valid. Stable slugs become read-only after first publication in v1.

### 3. Make the database the catalog, stock, and order authority

Conceptual models (final names can change without changing the specs):

| Record                                    | Responsibilities and constraints                                                                                                                                                                                                                                                                                                               |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Product                                   | Stable ID/slug, name, descriptions, category, optional audience/material/care fields, publication state, option definitions, revision, timestamps. Archive instead of delete.                                                                                                                                                                  |
| Variant                                   | Product ID, stable ID, normalized unique option combination, unique SKU, active state, positive integer USD price, tax classification, revision. Product with no options uses one default variant.                                                                                                                                             |
| ProductImage                              | Owned storage keys, validated media type/dimensions, ordered gallery position, cover flag, alt text, optional variant link, pending/ready/archived state. Multiple images per product.                                                                                                                                                         |
| StockBalance                              | Per variant `unsoldQty` and `heldQty`; available = unsold minus held. Constraints: integers, `0 <= heldQty <= unsoldQty`. Unsold means studio stock not yet sold, excluding paid units awaiting packing.                                                                                                                                       |
| InventoryMovement                         | Append-only unsold/held deltas, reason, actor/order/hold references, unique operation key, time. Reconcile counters against the ledger.                                                                                                                                                                                                        |
| Order / OrderItem                         | Separate payment/refund/fulfillment states; immutable item names, SKU, variant values, quantity, unit prices, tax classification; subtotal/shipping/tax/discount/total and currency; purchase email and shipping snapshots; unique Checkout Session/PaymentIntent associations. Lines are keyed by variant, allowing two sizes of one product. |
| CheckoutAttempt / Reservation             | Guest ownership binding, canonical request fingerprint, catalog quote revision, persistent provider payload/idempotency key, session ID, expected expiry, and held quantities. State distinguishes creating, active, consumed, released, and needs reconciliation.                                                                             |
| StripeEvent / Refund / Dispute / Shipment | Unique provider identities; processing state and retryable failures; financial history independent of physical stock; dispute attention/deadline; one shipment for the whole order in v1.                                                                                                                                                      |
| EmailOutbox / AuditEvent                  | Transactionally queued deduplicated confirmations/shipping notices and append-only operator/security actions; no secret or customer-address logging.                                                                                                                                                                                           |
| Auth tables / AdminStepUp / StoreSettings | Independently scoped sessions and admin role/TOTP; versioned shipping, tax, low-stock, and sales-enabled settings.                                                                                                                                                                                                                             |

Store money as integer cents, parse decimal dollar strings exactly, and display two decimals. Reject fractional/negative quantities and invalid combinations. Stock adjustments never overwrite `heldQty`. Reserve and mutate variant rows in a consistent ID order inside a database transaction, with bounded retries for serialization/deadlock conflicts. Whole-cart reservation is atomic.

Publication and stock are separate. A published product can be sold out; an archived variant remains resolvable for historical orders and existing holds but cannot enter a new checkout. Price changes apply to new quotes; an active session keeps its original snapshot. Stock-affecting actions use an operation key so retries cannot repeat them.

### 4. Separate reservations from payment and physical shipment

The browser cart stores versioned `{variantId, quantity}` lines, with no authoritative names/prices. Clear the old preview schema with an explanatory message. Resolve display content through a server quote and render text through safe DOM/template escaping. Reject empty, malformed, oversized, stale-price, inactive, or insufficient-stock carts with actionable line errors. Show and require acknowledgment of a changed price before starting a new checkout.

Checkout sequence:

1. Issue a short-lived, opaque checkout-attempt token scoped to an HttpOnly guest session and canonical cart quote. Enforce same-origin requests and distributed limits on repeated checkout/holds.
2. In one transaction, revalidate the quote, lock all variant balances, increase held stock, create the pending order and immutable items, and persist the exact Stripe request and its idempotency key. A repeated token returns this attempt; a changed cart uses a new attempt and cannot reuse the previous key/payload.
3. Outside the transaction, create a hosted Checkout Session from the stored server snapshots using per-line `price_data`. Embed store/order/variant metadata, server-controlled success/cancel URLs, a shipping-rate snapshot, and approved tax configuration. Disable Checkout quantity adjustment, promotion codes, recovery links, and delayed payment methods for launch. Stripe Price synchronization is not required for product editing/publication; Vesper's Stripe catalog publication routine is deliberately not copied. [Checkout Session API](https://docs.stripe.com/api/checkout/sessions/create).
4. Link the returned session, preserving unique identities. Double-clicks/network retries reuse the same attempt and Stripe key. A definite pre-creation failure releases the hold; a timeout or process crash after dispatch is uncertain and retains stock for reconciliation. Repeat the same persisted provider request/key within its supported retry window; never create another payable session to resolve uncertainty.
5. Target a short hosted session lifetime with a default 35-minute expiry, allowing dispatch headroom above Stripe's 30-minute minimum. Persist the exact expiry in the provider request and use the returned session's expiry as authority; do not change the payload on retry. A browser cancel/back redirect is informational. Explicit cancel asks the server to expire an open provider session and releases stock only after expiry is confirmed. [Stripe limited-inventory guidance](https://docs.stripe.com/payments/checkout/managing-limited-inventory.md?payment-ui=stripe-hosted).

Provider calls must not run inside row-lock transactions. A crash between local and provider writes is a first-class state, not a reason to silently release stock. A declined card is a failed attempt inside an otherwise open/retryable Checkout Session; it does not release the session's hold.

| Verified condition                                                   | Order/payment action                    | Inventory action                                                                                                                                            |
| -------------------------------------------------------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Active/open session                                                  | Pending, not packable                   | Keep hold                                                                                                                                                   |
| Completed but payment unpaid/processing                              | Processing/attention, not packable      | Keep hold until a definitive provider result; nominal expiry alone does not release it                                                                      |
| Completed and paid, or verified delayed success                      | Paid, ready to pack                     | Once only: unsold -= quantity and held -= quantity; consume reservation                                                                                     |
| Expired unpaid session or definitively failed closed payment/session | Expired/failed                          | Once only: held -= quantity; release reservation                                                                                                            |
| Duplicate completion/expiry/failure after paid                       | Preserve paid state                     | No additional movement                                                                                                                                      |
| Unknown provider result or mismatched store/order/amount             | Needs attention; block packing          | Retain unresolved holds and alert; do not infer payment                                                                                                     |
| Unexpected paid order after a previously confirmed release           | Paid / Needs attention until reconciled | Atomically reacquire/consume the whole cart if stock exists; otherwise block fulfillment and show an exceptional refund action, never create negative stock |

Verify Stripe signatures from the raw request body; validate mode, store identity, session/order/PaymentIntent binding, exact lines/quantities/prices, approved shipping selection/address, currency, and provider totals. Fetch current provider state and line items where needed, so old events cannot regress newer state. If the webhook wins the race before session-link persistence, only bind a session after all identities and the stored request match.

Payment transition, reservation movement, event completion, and confirmation outbox insertion occur in one transaction with unique constraints. Return success only after durable processing or durable retryable work; transient failures remain retryable. Duplicate deliveries, separate event IDs for the same payment, and concurrent workers converge on one order effect. A public success page reads status and never fulfills from query-string claims. [Stripe fulfillment guide](https://docs.stripe.com/checkout/fulfillment?payment-ui=stripe-hosted), [Webhook delivery rules](https://docs.stripe.com/webhooks).

Serve guest order status only with an unguessable capability bound to that order/guest session; a bare order ID or Checkout Session ID does not reveal email/address. Use no-store responses, token redaction, and a referrer policy. Cart clearing removes only the purchased attempt's matching quantities after authoritative paid status, preserving items added later.

### 5. Provide bounded, durable reconciliation and notifications

Add an authenticated maintenance endpoint invoked at least every five minutes. It leases work in bounded batches, reconciles uncertain/expired/processing checkout attempts against Stripe, retries pending provider events and email deliveries, and records its last successful run. Confirm provider terminal state before releasing a hold; a local timer alone cannot prove a session is unpayable. Request-path checks can reconcile a small number of overdue holds for affected variants but are not the only recovery mechanism.

Do not use process timers, in-memory queues, or unawaited background promises for correctness on the VPS. Notifications use a database outbox created with the business transaction and a private adapter to the guarded Good Apollo Mautic transport. Provider send success followed by local failure can still produce a rare duplicate; dedupe keys and provider idempotency where available reduce that risk. Reconcile uncertain provider outcomes before retrying. The operator sees delivery status and a retry action; payment/stock stay committed when email fails.

Monitor failed jobs, provider failures, stuck holds, ledger drift, database readiness, and unprocessed paid orders. Maintenance failure alerts after two missed five-minute intervals; uncertain sessions older than one hour surface attention. Unknown states fail closed for saleable stock, with an operator reconciliation action that follows the same provider checks.

The existing Senna n8n instance remains the five-minute scheduler, with source in `~/projects/infra/n8n/workflows/good-apollo-goods/maintenance.sdk.js`; it calls the authenticated commerce endpoint on the VPS. Keep that workflow inactive until production runtime, service credentials, and the matching secret are configured. Do not run duplicate schedulers. A production DNS cutover remains a separate release step after the VPS domain, TLS, routing, health, backup, and end-to-end evidence are verified.

### 6. Support practical shipping, refunds, and stock corrections

The launch has one flat USD shipping service configured in settings, `US` as the country allowlist, and separate processing and delivery wording. The flat service must cover all U.S. addresses accepted by the configured service, including Alaska/Hawaii; there are no state-specific rate rules or exclusions in v1. Hosted Checkout's country selector is not a state exclusion mechanism. If exclusions become necessary, revise the address collection/validation approach before implementation. No shipping amount is invented. Collect email, recipient name, and address in Checkout; persist the paid shipping selection and address in the order. Shipping amounts and tax behavior originate from settings/Stripe, never the browser. Stripe calculates applicable configured tax; selecting Stripe Tax does not establish the business's registrations. Live sales require a recorded tax configuration decision, including an explicit reason if automatic tax is disabled. [Stripe address country controls](https://docs.stripe.com/api/checkout/sessions/create).

Use tax-exclusive USD prices for launch and reject a cart below the provider's supported charge minimum before creating its hold/session. At payment acceptance, require reconciled subtotal + shipping + tax - discounts = total. Store line/provider allocations and shipping tax data without assigning the whole order total to the first line as Vesper currently does for its single-product case. Preserve address/financial/item snapshots after catalog/settings edits. Do not enable promotions in v1, but persist provider discounts as zero and reject unexpected mismatches.

Only paid, non-canceled, non-blocked orders enter To pack. A packing slip includes quantities, SKU/options, address, order reference, and processing notes, with no internal secrets. Mark shipped records one full-order shipment, carrier, tracking number, safe allowlisted tracking URL, and time; repeated submissions do not duplicate shipments or messages. Shipment has no stock effect because payment already consumed unsold stock.

Refunds have their own provider lifecycle and operation keys. Support full or selected monetary partial refunds up to the remaining paid amount, synchronized from app actions or Stripe Dashboard webhooks. Refund requests are not marked successful before provider confirmation. Full refunds block new shipment; shipped orders retain their shipping history. An unshipped cancellation stops packing and separately requests any required refund. A pending checkout cancellation first resolves/expires the provider session.

Serialize cancellation, shipment, and refund-request changes against the same order state so concurrent actions cannot silently ship a canceled order. If refund delivery precedes paid confirmation, retrieve current payment/refund state and retain the full-refund shipping block when recording the original payment. Track matching charge disputes as an attention state with provider deadline and a Stripe Dashboard link; block unshipped disputed orders until resolved and retain tracking/history for manual evidence submission. Dispute processing never restocks or masquerades as a refund. Automated dispute evidence submission is outside v1. [Stripe dispute evidence workflow](https://docs.stripe.com/disputes/visual-evidence).

Physical restocking is an explicit per-item action with quantity, reason, and idempotent history, capped by the quantity sold minus prior restocks. For an unshipped canceled order, the operator confirms the item is still present and sellable; for a returned item, confirms receipt/condition. A refund by itself never restocks. Support records do not rewrite the existing final-sale commercial intent; final public exception wording is an owner launch input.

### 7. Make photos manageable and safe

Use a dedicated Garage bucket/access key for each environment. Every intent belongs to an admin and product, with bounded content size/type and expiring ownership. The authenticated same-origin upload endpoint writes to Garage through the private Docker network, avoiding browser CORS and public Garage exposure. Never accept arbitrary remote image URLs.

Support JPEG, PNG, and WebP files up to a documented 10 MB limit, several photos per listing, and phone-browser selection. For unsupported formats such as HEIC, explain how to export/select JPEG and preserve the rest of the form; automatic HEIC conversion can be added after measuring the supported runtime. Upload preview is not publication readiness. On finalization verify bytes, decode content, enforce dimensions/pixel limits, normalize orientation, strip EXIF/GPS, and generate responsive WebP/thumbnail derivatives with immutable keys. A failed conversion remains pending/failed and cannot be used as a published cover.

Originals remain private. Deliver only sanitized derivatives through the configured image delivery route; previewing a draft requires admin authority. Ready published derivatives use immutable keys and can be cached publicly. Replacing/archiving an image updates references atomically and retains recoverable storage; orphan cleanup has a retention window and never deletes referenced files. Garage's single-node S3-compatible setup does not provide a bucket quota, so Good Apollo enforces a 4 GiB app-level budget by transactionally accounting for original and derivative bytes; host disk alerts and an independent encrypted backup protect the shared volume. Before uploads are enabled for a bucket with existing objects, reconcile their byte totals into the catalog. Back up database and object data together and restore them in a separate environment.

### 8. Adapt admin security without making ordinary editing cumbersome

Use independently configured Better Auth email sign-in and Vesper's admin-role plus session TOTP pattern, with a guided initial enrollment and recovery flow. Only pre-allowlisted operator mailboxes can become admins through an explicit bootstrap command; no public signup grants access. Check admin role and current eight-hour step-up on every page, mutation, upload intent, packing slip, and export. Validate same-origin/CSRF protections, rate limits, cookies, redirect allowlists, and session revocation. The Astro integration exposes standard request handlers; no Next.js-specific helpers are imported. [Better Auth Astro integration](https://better-auth.com/docs/integrations/astro).

Use labeled fields, keyboard controls including photo reorder buttons, mobile cards for wide inventory rows, visible save feedback, and persistent unsaved form data on validation/expiry. No repeated TOTP prompt for each product action during a valid admin session. Audit product publication/edits, stock, shipments, refunds, settings, and admin changes. Include actor, entity, operation, and bounded changed-field metadata; avoid addresses, secrets, upload URLs, and tokens in logs. Exports are admin-only and escape spreadsheet formula injection; stock export and order export do not substitute for backups.

## Risks / Trade-offs

- [Custom commerce adds maintenance responsibility] → Keep scope small, adapt reference tests, require transaction/recovery evidence and operator acceptance before launch; revisit hosted commerce if usability fails.
- [Last-unit stock can remain held during provider uncertainty] → Prefer no overselling; scheduled reconciliation, clear attention alerts, bounded provider retries, and verified manual resolution.
- [Manual off-site sale/consignment adjustments can be forgotten] → One obvious removal action with reason, low-stock view, and periodic stock count; no automatic external inventory claims.
- [Multi-service writes cannot be one transaction] → Persist exact attempts/provider keys and use recovery states; transactionally queue notifications rather than sending before commit.
- [A shared VPS can experience resource contention or a host outage] → Apply container CPU/memory limits, bound database connections/uploads/pixels/jobs, enforce the app-level media budget, alert on host disk pressure, retain off-VPS recovery copies, and pass production-like load and restore checks before launch.
- [Self-hosted object storage lacks provider-managed versioning, bucket quotas, and independent availability] → Use private per-environment Garage buckets/keys, the app-level media budget, host disk alerts, encrypted off-VPS backups, and a successful separate-environment restore before sales.
- [Current final-sale wording conflicts with operational refund exceptions] → Keep intent, record owner-approved support wording, and ensure technical remedies exist for failed fulfillment/duplicate charges.
- [No production services or final merchandise data have been verified here] → This is an implementation-ready plan; the launch evidence packet must verify configuration, real stock/photos, email, and restore capability later.

## Migration Plan

1. Build the standalone Node runtime and configure the resource-capped VPS service, persistence/configuration, migrations, auth bootstrap, Garage storage, Mautic delivery adapter, and tests in isolated development/preview environments. Keep all sale flags disabled.
2. Import existing product metadata as drafts with zero unsold stock, stable slugs, and placeholders explicitly marked non-publishable. Seeds are idempotent and never overwrite operator edits/counts. Replace every catalog consumer and migrate/clear legacy cart storage.
3. Implement admin/catalog first, then ledger/reservations, Stripe/payment recovery, and fulfillment/outbox. Validate each vertical slice with disposable database fixtures and original test images.
4. Deploy a protected preview with isolated database/storage/auth credentials and Stripe test configuration on the VPS. Exercise delayed/duplicate/out-of-order events even though delayed methods are disabled for launch. Verify the Node runtime, resource limits, upload path, customer-facing cache behavior, and canonical routes without affecting other services.
5. Complete operator timed tasks on mobile/desktop and keyboard; adjust the UI until the primary operator succeeds. Supply real photos, confirmed prices/counts, shipping settings/promises, contact mailbox, and approved policies.
6. Configure the isolated production runtime on the existing VPS, authenticated five-minute n8n scheduler, webhook endpoint, sender DNS, Good Apollo database roles, Garage bucket/key, and Mautic delivery path. Enforce container and storage limits. Back up database plus Garage data to an independent encrypted destination and restore a sample gallery/order/ledger into a separate environment; document a maximum 24-hour backup loss window and four-hour restore target.
7. Produce redacted launch evidence: test-mode cart/payment, last-unit race, timeout recovery, invalid signatures, mode/store rejection, email retries, packing/tracking/refund/restock, readiness, alerts, HTTPS/domain redirects, policies, and restore. Resolve every failure before enabling public sales.
8. At the actual release, enable verified live configuration and public checkout together; allow indexing only on public published pages, add sitemap/product structured data with real availability, and retain noindex for admin/cart/private/preview routes. Verify live endpoint configuration without a synthetic real charge. A legitimate first order can validate the full live lifecycle after launch.

Rollback: disable new checkout first, preserving webhook and maintenance processing for already-open/paid sessions. Deploy the previous compatible application release against forward-compatible schema. Never reset stock or restore an old database over new orders. If payment/inventory integrity is uncertain, keep sales paused, reconcile provider sessions and ledger, and resume only after counts agree. Record database snapshot and application revision for each release.

## Open Questions

These are configuration/content inputs within the selected approach, not unresolved architecture:

- What VPS CPU/memory budget, Garage volume limit, alert thresholds, backup destination/retention, and off-host restore process will protect the rest of the shared stack?
- Which Mautic transactional templates/routes and sender DNS outcomes must be approved for buyer/operator messages, and which stock alert threshold should be configured?
