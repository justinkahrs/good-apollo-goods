# Commerce architecture

Implementation uses Astro 7 with the standalone Node adapter on the selected VPS runtime. Existing informational URLs and brand tokens remain. Catalog, product, shipping, cart, admin and API routes render on demand. The public domain routes to the VPS; Vercel remains available for rollback and Netlify remains a canary through acceptance.

## Accounts and isolation

Owner decisions: U.S. only, guest checkout, ready-to-ship stock; a Good Apollo admin; separate database and object storage; shared Stripe account; initial administrator `hello@annakahrs.com`.

Selected production direction: standalone Node on the existing `senna-infra` VPS; a dedicated `good_apollo_goods` database with separate migration/runtime roles on shared PostgreSQL; per-environment private Garage buckets and scoped keys; the guarded Good Apollo Mautic sender route; and the existing Senna n8n instance as the five-minute scheduler. Its source is `~/projects/infra/n8n/workflows/good-apollo-goods/maintenance.sdk.js`; it remains inactive until the commerce runtime and production secret are configured. The app enforces a configurable 4 GiB default media budget, while a host disk warning at 90% used (10% free) and independent encrypted off-VPS backups protect the shared storage. Reconcile existing object bytes into the database accounting field before enabling media uploads in any bucket that already contains Good Apollo objects. Garage does not provide S3 object versioning, and its official single-node quick start warns that single-node operation has no data redundancy; encrypted off-VPS media/database backups and a separate restore are launch requirements. The public domain remains on its current host until the VPS site is verified live. Protected preview requires separate test database/storage/auth secrets and Stripe test mode. SMTP is local-development-only; production order/account/shipment messages require the separate authenticated commerce route into the Mautic transport. Commerce and newsletter gates remain closed. The prior Netlify deployment and Vercel project are preserved as rollback/history until public VPS acceptance and DNS cutover.

Use a migration identity with DDL privileges and a separate runtime identity with only required DML. Runtime must not have `TRUNCATE`, schema ownership or permission to disable triggers. Both database URLs must use TLS certificate verification and resolve to the isolated Good Apollo database. Keep Garage originals and derivatives private; authenticated uploads pass through the same-origin app endpoint, and the app serves only verified, published derivatives to shoppers. The app key is scoped to the Good Apollo bucket, never Vesper's bucket. Garage does not support S3 object versioning; encrypted off-VPS backups and restore evidence are required. Garage's S3/admin interfaces stay on the private VPS Docker network, so browser CORS is not configured.

The VPS, shared PostgreSQL, Garage and Mautic are existing self-hosted services; no new hosting or storage plan is part of the selected setup. The app-level media budget defaults to 4 GiB (`MEDIA_BUDGET_BYTES`) and must stay below measured host headroom; configure and verify the 90%-used (10%-free) disk warning notification and independent backups before production media is enabled. n8n supplies the five-minute trigger, while maintenance executes inside the Good Apollo Node service. A protected preview and restore must show that this workload stays within the host's resource budget.

## Local setup

Node 22.12+ is required. Install with `npm ci`; postinstall generates Prisma 7.10. Keep matching Prisma client/adapter/CLI versions pinned. Stripe 22.6 and Better Auth 1.7 are pinned. Transitive security overrides are in package.json and must be checked when dependencies change.

On this Mac, `npm run local:setup` creates independent `good_apollo_dev` and `good_apollo_test` databases and a non-superuser role using the existing Homebrew PostgreSQL. It preserves existing `.env` entries and writes random independent secrets privately. On another machine, create those two databases with your PostgreSQL tools and fill `.env` from `.env.example`. Do not point tests at customer data.

Run `docker compose up -d` for isolated LocalStack S3 and Mailpit. Run `npx tsx scripts/setup-storage.ts`, `npm run db:migrate`, `npm run db:seed`, and `npm run admin:bootstrap`. The seed imports four existing products as private drafts, with zero stock and blocked placeholders. Running it again preserves edits and balances. Start `npm run dev` on port 4371. Local mail is visible at `http://localhost:18025`. Local media is at port 19000 and is not a production service.

`npm test` requires `TEST_DATABASE_URL` to end in `_test` on localhost and runs migrations there. It deliberately truncates only that disposable database. `npm run check`, `npm run build`, and `npm run build:local` validate source and both adapters. `npm run start:local` starts the local production build. `npm run maintenance` invokes durable recovery manually. CI uses disposable PostgreSQL, S3 and mail services.

After `build:local`, install Chromium with `npx playwright install chromium` and run `npm run test:browser`. It starts the built server on port 4372 and uses the disposable test database; run it sequentially after integration tests. `npx tsx scripts/verify-validation.ts` proves a deliberate assertion failure is detected and deletes the temporary probe. `npx tsx scripts/restore-drill.ts` verifies encrypted synthetic history/media recovery in separate local resources.

## Data and invariants

Money is integer USD cents; forms parse dollars exactly. Product and variant revisions reject stale edits. Published product slugs remain fixed. Publication requires a description, a positive active variant and verified real described photos; sold-out listings are allowed. Duplicate products are independent drafts with zero stock. Upload intents belong to a product and operator, expire in ten minutes and allow at most 10 MB of JPEG/PNG/WebP. Sharp decodes with a 36-million-pixel limit, applies orientation and produces metadata-free 400/800/1200 WebP derivatives. HEIC needs export to JPEG.

Each variant has unsold and held counts; available is unsold minus held. Unsold excludes units already paid for, even when they remain in the packing area. Ordered row locks and serializable bounded retries reserve an entire cart atomically. Database checks prevent negative quantities and holds exceeding unsold. The stock ledger is append-only and uniquely keyed per business operation. Paid confirmation consumes unsold and held once. Verified unpaid expiration releases held only. Shipping and refunds do not move stock. Restocking requires explicit presence, sellable condition and sold-minus-prior-restocked bounds.

## Payment boundaries

Browser storage contains a bounded versioned variant/quantity cart. It does not authorize prices. Quotes resolve current products, variants, revisions and settings; signed quotes expire in ten minutes and belong to a private guest cookie. On checkout, the server saves the immutable order/items/settings, exact provider request and stable idempotency key before making any Stripe call. A timeout retains holds and repeats the same request/key; it never starts a second independent session. The default session expires after 35 minutes. Returning through a cancel link does not release stock; explicit cancellation asks Stripe to expire the session first.

Stripe receives per-line price data, exact USD amounts, U.S. address collection, one flat shipping rate, exclusive tax and card payments/eligible wallets. Adjustable quantity, promotions, recovery links and delayed payment methods are disabled. Store/order/attempt and line metadata scope the shared Stripe account. A dedicated endpoint secret is required: copying Vesper's webhook secret is incorrect. Payment reconciliation retrieves current provider state and verifies identity, lines, quantities, prices, address and totals before the paid/stock/outbox transaction. Paid history is monotonic. Late payment after release reacquires the entire cart if possible; insufficient stock creates paid attention and blocks packing.

Defaults are **$6.95 uniform U.S. shipping** and **3–5 business day processing**. Both are configurable in Settings. Automatic tax is enabled as the proposed default but `taxConfigured` starts false. The operator must verify registrations/configuration and record the decision before checkout opens. Product tax categories are configurable; the exact mappings come from [Stripe's tax code list](https://docs.stripe.com/tax/tax-codes). Stripe calculates tax only for applicable configured registrations. No registration was inferred from the owner's belief that automatic tax was configured.

Guest status uses a private capability plus the same guest cookie, not a bare order/session ID. Purchased quantities are removed only for the matching checkout; later cart additions are retained. Private routes use no-store/no-referrer and no indexing. No order addresses, token values or private upload credentials belong in logs.

## Authentication and notifications

Better Auth magic-link signup is disabled. Bootstrap establishes only the allowlisted operator; sessions and secrets are independently scoped. Every business page/read/mutation/export checks a verified admin email/role and current-session TOTP step-up of at most eight hours. Sessions are read from the database without a cookie cache, so revocation takes effect immediately. Enrollment/recovery screens expose no business records. Mutation origin checks and persisted limits apply across instances. Provider/auth logs are disabled or replaced with bounded status codes.

Business notifications enter a persistent outbox within the order/shipment transaction. Delivery uses leases and exponential retries with stable Message-ID and transition dedupe. SMTP cannot guarantee exactly-once delivery across a crash after provider acceptance but before the database acknowledgement; rare duplicate delivery is possible, while duplicate intended notification records are prevented. Payment correctness never depends on successful email delivery.

Authenticator enrollment returns a locally generated QR PNG, a Base32 manual setup key, the full setup URI, and recovery codes from the protected auth handler. The page clearly labels the key for Google Authenticator's manual **Enter a setup key** flow and provides a copy action for mobile setup. It keeps the full URI in an advanced disclosure and displays the QR image without importing a QR-code bundle, so an unavailable optimized browser dependency cannot prevent setup. Enrollment responses are private/no-store and retain Better Auth's cookies. The setup button shows progress, prevents repeated creation while pending or ready, and allows retry after failure. No QR service receives the secret. Browser regression covers the actual setup button and loaded image; security integration covers enrollment through the HTTP handler, TOTP verification and single-use recovery.

`ADMIN_EMAIL=hello@annakahrs.com` is the primary operator and notification mailbox. Optional `ADDITIONAL_ADMIN_EMAILS` is a validated comma-separated allowlist, combined with the primary address, normalized and deduplicated. Bootstrap creates only those operator accounts; each needs verified email and its own current-session authenticator verification. The owner authorized `justin@justinkahrs.com` for local testing through the private `.env`; no extra admin is enabled by default. Removing it from configuration and restarting revokes protected access even for an existing admin session. `SUPPORT_EMAIL` defaults to the existing public contact `hello@goodapollogoods.com` and is the reply-to on business mail. Verify both mailbox/sender delivery before launch. Five-minute maintenance and an independent health monitor are required; stale work or inventory drift closes new checkout without disabling recovery.
